# V2.2.1 — Financial Foundation

## Objective
Build profitability from traceable source records rather than a second disconnected bookkeeping system.

## Source-of-truth model
- `sales_records` = revenue.
- `farm_expenses` = cash expenses and direct operating expenses.
- `stock_transactions` = inventory movement; V2.2 adds a cost snapshot for each transaction.
- `production_cycles` = optional profitability boundary.
- `financial_allocations` = controlled allocation of shared/farm-level expenses to cycles.

## Feed costing
Feed usage is recognized as production cost at the inventory item's weighted-average cost at the moment of use. The transaction stores `unit_cost` and `total_cost`, so later price changes do not rewrite historical cost.

Feed purchases remain cash expenses. They are intentionally not added again to consumed-feed production cost, preventing double counting.

Historical feed-use transactions before V2.2 have no cost snapshot and are excluded from consumed-feed cost rather than inventing a historical cost.

## Cycle attribution
New poultry and ruminant feed-use transactions can optionally be assigned to an active production cycle. This enables cycle-level feed cost and later KPIs such as feed cost/bird, feed cost/egg and cost/kg.

## Shared expenses
A farm-level expense can be split across cycles using `financial_allocations`. Direct cycle expenses are counted in full; allocated shared expenses contribute only their allocated amount.

## First user-facing feature
`management/profitability.php` provides monthly/cycle profitability using:

**Revenue − feed consumed cost − other operating cost = operating result**

The page also warns when historical feed transactions are uncosted.

## Deliberately deferred
- Full poultry unit economics.
- Ruminant animal-level economics.
- Trend/anomaly intelligence.
- Forecasting.
- Automated allocation recommendations.
- SaaS billing/commercial analytics.

## Release safeguard: frontend dependency contract

Interactive pages depend on the local Bootstrap, jQuery and DataTables assets. The release package must include those assets; omitting them causes a broad UI failure where modal, edit, dropdown and calendar controls stop responding.

Run before deployment:

```bash
php tests/frontend_asset_contract.php
```

The test fails if a referenced local asset or a required interactive dependency is missing. This is a packaging guard and should be part of every future V2.2/V2.3 release build.
